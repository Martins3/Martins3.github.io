# Linux图形栈简介（第一部分）翻译

2023 年 12 月 19 日

本文由 Thomas Zimmermann 供稿

Linux 图形开发者在提到一系列独立软件组件及其交互方式时，常常会说起*现代*Linux 图形。这其中，既包含内核管理的显示资源、用于合成的 Wayland、硬件加速的 3D 渲染，当然，它明确不包含 X11。在这个分为两部分的系列文章中，我们将快速浏览图形代码，了解它如何将应用数据转换为像素数据并显示在屏幕上。在本篇中，我们将介绍应用渲染、Mesa 内部机制，以及必要的内核特性。

#### 应用渲染

图形输出始于应用程序，它会处理并存储待可视化的格式化数据。用于可视化的通用数据结构是**场景图**，这是一种树形结构，每个节点要么存储 3D 空间中的模型，要么存储模型的属性。模型节点包含待可视化的数据，比如游戏的场景，或是科学模拟的元素。属性节点则设置模型的方向或位置，每个属性节点都会作用于它下方的所有节点。为了将场景图渲染为屏幕上的图像，应用会从上到下、从左到右遍历这棵树，设置或清除属性，然后据此渲染 3D 模型。

在下方的示例场景图中，渲染从根节点开始，根节点会初始化渲染器并设置输出位置。应用首先处理左侧分支，在位置 \(0, 0\) 处，使用纹理 1 中存储的表面图案渲染 “矩形 1”。随后应用回到根节点，处理右侧分支，进入名为 “变换” 的属性节点。应用会用 4×4 矩阵来描述定位、缩放这类变换，渲染算法会在处理过程中应用这些矩阵。在这个例子中，变换节点会将它所有的子节点都缩放 0\.5 倍。因此，渲染 “矩形 2” 和 “矩形 3” 时，它们会以原尺寸的一半显示，位置也分别调整为 \(10, 10\) 和 \(15, 15\)。这两个矩形分别使用了不同的纹理：纹理 2 和纹理 3。

为了简化渲染并利用硬件加速，大多数应用都会使用标准 API，比如 OpenGL 或 Vulkan。不同 API 的细节各有不同，但它们都提供了用于管理图形内存、向其中填充数据，以及渲染存储信息的接口。最终得到的图像，应用可以直接显示，也可以作为输入数据用于进一步处理。

所有图形数据都存储在缓冲对象中，每个缓冲对象都是一段带有句柄或 ID 的图形内存区域。比如，每个 3D 模型都存储在**vertex\-buffer object**中，每个纹理存储在**texture\-buffer object**中，每个对象的**surface normals**也都存储在缓冲对象中，以此类推。输出图像本身也存储在缓冲对象中。因此，图形渲染在很大程度上可以说是内存管理的工作。

应用可以以任意格式提供输入数据，只要图形着色器能够处理即可。**着色器**是一个程序，其中包含将输入数据转换为输出图像的指令。它由应用提供，由显卡执行。

实际的着色器程序可以实现复杂的多通道算法，但在这个例子中，我们将其简化到最基础的部分。着色器中最常见的两个操作大概就是顶点变换和纹理采样了。我们可以把顶点理解为多边形的角点。用 OpenGL 着色语言（GLSL）编写的话，顶点变换的代码如下：

```glsl
uniform mat4 Matrix; // 对矩形的所有顶点都相同
 in vec4 inVertexCoord; // 每次调用时传入不同的顶点坐标

 gl_Position = Matrix * inVertexCoord;
```

变量`inVertexCoord`是来自应用场景图的输入坐标，而`gl\_Position`则是应用输出缓冲中的坐标。广义来说，前者是待显示场景内的坐标，后者是应用窗口内的坐标。`Matrix`是 4×4 矩阵，描述了这两个坐标系之间的变换。这个着色器操作会为场景图中的每个顶点执行一次。在之前的矩形场景图例子中，`inVertexCoord`至少会包含每个矩形的每个顶点一次。而矩阵`Matrix`则包含了对应顶点的变换信息，比如将它移动到正确的位置，或是按照变换节点的要求缩放 0\.5 倍。

当顶点被变换到输出坐标系后，着色器程序会计算被覆盖的 “片元” 的数值 —— 这是图形领域的术语，指的是带有 Z 轴深度值以及其他信息的输出像素。每个片元都需要颜色。在 GLSL 中，着色器的`texture\(\)`函数会从纹理中获取颜色，代码如下：

```glsl
uniform sampler2D Tex; // 当前矩形的纹理对象
 in vec2 vsTexCoord; // 该片元的插值纹理坐标

 Color = texture(Tex, vsTexCoord);
```

这里，`Tex`代表纹理缓冲，`vsTexCoord`是纹理坐标，也就是在纹理中读取数据的位置。通过这两个值，`texture\(\)`会返回一个颜色值，将它赋值给`Color`就会向输出缓冲中写入一个带颜色的像素。为了用像素数据填满输出缓冲，这段着色器代码会为每个独立的片元执行一次。纹理缓冲由当前绘制的模型指定，纹理坐标则由 OpenGL 的内部计算提供。对于示例中的场景图，应用会为每个矩形调用这段代码，使用对应矩形的纹理缓冲。

在整个场景图上运行这些着色器指令，就会生成应用的完整输出图像。

#### Mesa

到目前为止，我们讨论的内容都不是 Linux 特有的，但这些内容为我们了解它的实现方式提供了框架。在 Linux 上，Mesa 3D 库（简称 Mesa）实现了 3D 渲染接口，同时为各类图形硬件提供支持。对应用来说，它为桌面图形提供了 OpenGL 或 Vulkan，为移动系统提供了 OpenGL ES，为计算任务提供了 OpenCL。在硬件侧，Mesa 为如今大多数图形硬件实现了驱动。

Mesa 驱动通常不会自己实现这些应用接口，因为 Mesa 本身已经提供了大量辅助工具和抽象层。对于有状态的接口，比如 OpenGL，Mesa 的 Gallium3D 框架会将接口和驱动连接起来，这被称为状态跟踪器。Mesa 为不同版本的 OpenGL、OpenGL ES 和 OpenCL 都提供了状态跟踪器。当应用使用 API 时，它会修改对应接口的状态跟踪器。

Mesa 中的硬件驱动会进一步将状态跟踪器的信息转换为硬件状态和渲染指令。比如，调用 OpenGL 的`glBindTexture\(\)`会在 OpenGL 状态跟踪器中选中当前的纹理缓冲，随后硬件驱动会将 texture\-buffer object 加载到图形内存中，并将活动的着色器程序关联到这个缓冲对象，将它作为自己的纹理。在我们之前的例子中，这个纹理就会在着色器程序中作为`Tex`可用。

Vulkan 是无状态接口，因此 Gallium3D 对这类驱动没有帮助；Mesa 转而提供了 Vulkan 运行时来辅助它们的实现。不过，如果某个硬件有可用的 Vulkan 驱动，那它可能完全不需要基于 Gallium3D 的 OpenGL 支持。Zink 是一个 Mesa 驱动，它将 Gallium3D 映射到 Vulkan。通过 Zink，OpenGL 状态会先转换为 Gallium3D 状态，再通过标准 Vulkan 接口转发给硬件。原则上，这可以适配任意硬件的 Vulkan 驱动。我们可以想象，未来 Mesa 中的新驱动可能只会实现 Vulkan，然后依靠 Zink 来提供 OpenGL 兼容性。

除了 Gallium3D，Mesa 还为硬件驱动提供了更多辅助工具，比如 winsys 或 GBM。winsys 封装了窗口系统的细节，而 GBM（通用缓冲管理器）则简化了缓冲对象的分配。应用还可以使用多种着色器语言，比如 GLSL 或 SPIR\-V。Mesa 会将应用提供的着色器代码编译为 “新接口表示”（NIR），Mesa 驱动再将 NIR 转换为硬件指令。为了让着色器指令和相关数据能被 Mesa 的硬件加速处理，它们的缓冲对象必须存储在显卡可访问的内存位置中。

#### 内核内存管理

所有显卡可访问的内存，通常都被归为图形内存这个统称；它是图形栈的核心资源，因为栈中的所有组件都会和它交互。在硬件侧，图形内存有多种配置：从独立显卡上的专用内存，到片上系统（SoC）主板的普通系统内存。介于两者之间的，还有带有可 DMA 或共享图形内存的图形芯片、独立设备的图形地址重映射表（GART）内存，或是板载显卡的所谓 “stolen 图形内存”。

作为系统级的资源，图形内存由内核的**Direct Rendering Manager**（DRM）子系统维护。为了访问 DRM 功能，Mesa 会打开显卡在`/dev/dri`下的设备文件，比如`/dev/dri/renderD128`。根据用户空间组件的需求，DRM 以缓冲对象的形式暴露图形内存，每个缓冲对象都代表可用内存的一个切片。

DRM 框架为最常见的场景提供了多种内存管理器。AMD、NVIDIA 以及（即将支持的）Intel 的独立显卡的 DRM 驱动，都使用**Translation Table Manager**（TTM）。它支持独立图形内存、GART 内存和系统内存。TTM 可以在这些区域之间移动缓冲对象，因此如果设备的专用内存被占满，未使用的缓冲对象就可以被交换到系统内存中。

简单 framebuffer 设备的驱动通常会使用 SHMEM 辅助工具，它会在共享内存中分配缓冲对象。在这里，普通的系统内存会作为设备有限资源的影子缓冲。图形驱动会在内部维护设备的图形内存，但向外部暴露系统内存中的缓冲对象。这也让 USB 或 I2C 总线上的设备的缓冲对象可以被内存映射，即使这些总线不支持设备内存的页映射 —— 我们可以转而映射影子缓冲。

另一种常见的分配器是 DMA 辅助工具，它在物理内存的可 DMA 区域中管理缓冲对象。这种设计常用于 SoC 主板，这类主板上的图形芯片会通过 DMA 操作读取和存储数据。当然，有额外需求的 DRM 驱动可以选择扩展现有的内存管理器，或是实现自己的。

用于管理缓冲对象的 ioctl \(\) 接口被称为**Graphics Execution Manager**（GEM）。每个 DRM 驱动都会根据自身硬件的特性和需求实现 GEM。GEM 接口允许将缓冲对象的内存页映射到用户空间或内核地址空间，允许将页固定在某个位置，或是将它们导出给其他驱动。比如，用户空间的应用可以通过在 DRM 设备文件的文件描述符上，使用正确的偏移量调用`mmap\(\)`，来获取缓冲对象的内存页。这个调用最终会进入 DRM 驱动的 GEM 代码，由它来完成映射。我们接下来会看到，这个功能对软件渲染非常有用。

GEM 没有提供的一个通用操作是缓冲分配。每个缓冲对象都有特定的用例，这会影响（同时也受影响于）对象的分配参数、内存位置，或是硬件约束。因此，每个 DRM 驱动都会提供一个专用的 ioctl \(\) 操作来分配缓冲对象，以处理这些硬件特有的设置。Mesa 中对应的 DRM 驱动会相应地调用这个 ioctl \(\) 操作。

#### 渲染操作

仅仅拥有用于存储输出图像、输入数据和着色器程序的缓冲对象是不够的。要开始渲染，Mesa 会指示 DRM 将所有必要的缓冲对象放入图形内存，然后调用活动的着色器程序。这部分同样是硬件特有的，由每个 DRM 驱动单独以 ioctl \(\) 操作的形式提供。和缓冲分配一样，Mesa 中的硬件驱动会调用 DRM 驱动的 ioctl \(\) 操作。对于基于 Gallium3D 的 Mesa 驱动，这会在驱动将状态跟踪器信息转换为硬件状态时发生。

理想情况下，图形驱动只作为用户空间的应用和硬件之间的代理。硬件渲染器会和图形栈的其他部分异步运行，只有在出错或是成功完成时才会向驱动报告；这很像系统 CPU 在发生页错误或非法指令时通知操作系统。只要没有需要报告的内容，驱动的开销就会非常小。当然也有例外：比如旧型号的 Intel 显卡不支持顶点变换，因此 Mesa 中的驱动必须用软件来实现这些变换。而在树莓派上，内核的 DRM 驱动必须验证每个着色器的内存访问，因为 VideoCore 4 芯片没有 I/O MMU 来将着色器和系统隔离开。

#### 软件渲染

到目前为止，我们都假设存在图形渲染的硬件支持。如果没有这样的支持，或是用户空间应用无法使用它，会发生什么？比如，用户空间的 GUI 工具包可能更倾向于软件渲染，因为像 OpenGL 这类以硬件为中心的接口不符合它的需求。还有 Plymouth，这个程序会在启动时显示开机 logo，并提示输入磁盘加密密码，它通常无法使用完整的图形栈。对于这些场景，DRM 提供了 dumb\-buffer ioctl \(\) 接口。

通过使用 dumb 缓冲，应用可以在图形内存中分配缓冲对象，但不支持硬件加速。因此，返回的缓冲对象只能用于软件渲染。用户空间的应用，比如 GUI 工具包或 Plymouth，会将缓冲对象的页映射到自己的地址空间，然后将输出图像复制进去。Mesa 的软件渲染器的工作方式也类似：输入缓冲对象都位于系统内存中，由系统 CPU 处理着色器指令。输出缓冲则是一个 dumb 缓冲对象，用于存储渲染后的图像。虽然这既不快也不花哨，但它足以在不支持加速渲染的简单硬件上运行现代桌面环境。

到这里，我们已经梳理了应用侧的图形渲染栈。在完成场景图的遍历后，应用的输出缓冲对象中就包含了它想要显示的可视化场景或数据。但这个缓冲还没有出现在屏幕上。无论它是加速缓冲还是 dumb 缓冲，要将缓冲显示到屏幕上，都需要合成和模式设置，这是图形栈的另一半。在第二部分中，我们将介绍 Wayland 合成、使用 DRM 设置显示模式，以及图形栈的其他一些特性。

# Linux 图形栈简介，第二部分

2023 年 12 月 28 日

本文由 Thomas Zimmermann 供稿

要将应用的图形输出显示到屏幕上，需要在各个组件之间正确同步合成与模式设置，同时保证低开销。在这个系列的第二篇，也是最后一篇文章中，我们将介绍 Linux 图形栈的这些部分。在上一篇中，我们追踪了图形数据的流转路径：从应用出发，经过 Mesa，同时使用内核 Direct Rendering Manager（DRM）子系统的内存管理特性。最终我们得到了存储在输出缓冲中的应用图形数据，现在，是时候将这张图像展示给用户了。

#### 合成

用户空间的应用几乎不会自己显示输出，而是会指示屏幕合成器来完成这项工作。合成器是一个系统服务，它接收每个应用的输出缓冲，将它们绘制为屏幕上的图像。布局取决于合成器的具体实现，但堆叠和平铺是最常见的两种方式。合成器还负责收集用户输入，并将其转发给当前焦点应用。

过去，合成以及图形栈中几乎所有其他功能，都是由 X Window System 提供的，它实现了一个用于在屏幕上显示图形的网络协议。但由于它还要包揽绘制、模式设置、屏幕共享，甚至打印这些功能，X 存在软件臃肿的问题，很难适配图形硬件和 Linux 系统的变化；因此我们需要一个轻量级的替代方案。它的现代继任者是 Wayland，这同样是一种客户端 \- 服务器架构，每个应用都会作为客户端，使用合成器提供的显示服务。Wayland 的参考合成器是 Weston，但 GNOME 的 Mutter 或是 KDE 的 KWin 更为常用。

Wayland 中没有绘制或打印功能；它的协议只提供合成所需的功能。一个 Wayland 表面代表一个应用窗口，它是应用用于显示输出、从合成器接收输入事件的句柄。附加在表面上的是一个 Wayland 缓冲，其中包含可显示的像素数据，以及颜色格式和尺寸信息。这些像素数据就来自客户端应用渲染完成的输出缓冲。当修改表面附加的缓冲对象，或是修改它的内容时，应用会向合成器发送一个 Wayland 协议的表面损坏消息，合成器据此更新屏幕内容 —— 可能会使用新缓冲对象的内容。此时，应用的输出缓冲就变成了 Wayland 合成器的输入缓冲。

合成器中的渲染，和我们在第一篇中介绍的应用渲染的工作方式完全一致。合成器会维护一个列表，包含所有代表应用窗口的 Wayland 表面。这些窗口，加上合成器自身的界面元素，又构成了一个新的**场景图**。背景层包含壁纸图像、背景图案或是纯色。在背景之上，合成器会绘制应用窗口。实现这一点最简单的方式，就是为每个窗口绘制一个矩形，然后将应用提供的缓冲对象作为纹理图像使用。

在应用窗口之上，合成器会绘制自己的用户界面，比如用户可以和合成器交互的任务栏。最顶层则是用户当前交互的指示器；在桌面系统上，这通常就是鼠标指针。和应用一样，合成器也会使用常规的用户空间接口来渲染，比如 Mesa 的 OpenGL 或 Vulkan。

让这一切成为可能的最后一个模块，是缓冲对象的传输机制。和 X 不同，Wayland 应用始终和它们的合成器运行在同一台主机上。因此实现可以针对这种场景做优化：不需要网络编码、缓冲压缩这类操作。

对于传输位于系统内存中的缓冲对象，应用会创建一个引用该缓冲内存的文件描述符，通过连接的流套接字将它发送出去（这是一个单次的低开销消息），然后让合成器将这个文件描述符的内存页映射到自己的地址空间。这样，应用和合成器就建立了一个低开销的通道来交换像素数据。应用向共享内存区域写入数据，合成器从中读取数据进行渲染。实际使用中，我们也常常用多个缓冲对象来实现双缓冲。Wayland 的表面损坏消息则作为低开销的同步方法。

通过共享内存传输数据，对于软件渲染来说已经足够了，但对于高性能的硬件渲染来说，这还不够。如果用这种方式，应用需要先在图形硬件上完成渲染，然后通过缓慢的硬件总线将结果读回到共享内存区域中。

为了避免这个开销，图形缓冲必须保留在图形内存中。Wayland 提供了一个协议扩展，通过 Linux dma\-buf 来共享缓冲对象。dma\-buf 代表一种可以在硬件设备、驱动和用户空间程序之间共享的内存缓冲。应用会像第一篇中介绍的那样，通过 Mesa 接口使用硬件加速渲染自己的场景图，但它不会发送共享内存的引用，而是发送一个 dma\-buf 对象，这个对象引用的缓冲对象此时还位于图形内存中。Wayland 合成器可以直接使用这些存储的像素数据，完全不需要通过硬件总线读取它们。

硬件加速渲染本质上是异步的，因此需要同步。当应用向 Mesa 发送当前帧的最终渲染命令后，我们无法保证硬件已经完成了渲染。这是有意设计的，也是高性能的必要条件。但如果合成器在硬件完成渲染之前就显示缓冲对象的内容，就会导致输出失真。为了避免这种情况，硬件会在渲染完成时发出信号，这被称为栅栏（fencing），对应的 data structure 就叫做栅栏（fence）。这个栅栏会附加在应用传输给合成器的 dma\-buf 对象上。合成器会等待栅栏发出完成信号，之后才会使用这些数据来生成自己的输出。

#### 像素到显示器

在渲染完屏幕图像之后，合成器需要将它展示给用户。DRM 的模式设置代码控制着从图形内存读取像素数据、并将其发送到输出设备的所有环节。为此，每个驱动都会设置一个管道，用来模拟像素数据在图形硬件中的流转。管道的每个阶段都代表一个硬件功能模块，处理送往显示器的像素数据。

必要的最小阶段包括 framebuffer、plane、CRTC、encoder 和 connector，我们会在下面分别介绍。要让显示输出正常工作，每个阶段都必须至少有一个活动实例。但大多数硬件都会提供超出最小需求的功能，允许我们随意启用或禁用管道阶段。DRM 框架为每个阶段都提供了软件抽象，驱动可以基于这些抽象来开发。

管道的第一个阶段是 DRM framebuffer。它是存储合成器屏幕图像的缓冲对象，同时包含图像的颜色格式和尺寸信息。每个 DRM 驱动都会用这些信息来配置硬件，同时将硬件的指针指向缓冲对象的第一个字节，这样硬件就知道去哪里找像素数据了。

读取像素数据的过程叫做 scanout，对应的像素数据缓冲对象叫做 scanout 缓冲。每个 framebuffer 的 scanout 缓冲数量，取决于 framebuffer 的颜色格式。很多格式，比如常见的基于 RGB 的格式，会将所有像素数据存储在单个缓冲中。而对于其他格式，比如基于 YUV 的格式，像素数据可能需要拆分到多个缓冲中。

根据硬件的能力，framebuffer 可以比输出的显示模式更大或更小。比如，如果显示器被设置为 1920x1080 像素，它可能只显示一个大得多的 framebuffer 的一部分。或者，如果 framebuffer 比显示模式小，那它可能只覆盖显示器的一小部分，剩下的区域留空。因此，管道的下一个阶段会在整个屏幕中定位 scanout 缓冲。在 DRM 的术语中，这被称为 plane。它会设置 scanout 缓冲的位置、方向和缩放系数。根据硬件的不同，我们可以同时有多个活动 plane，每个使用不同的 framebuffer。所有活动 plane 的像素输出，都会送入管道的第三个阶段 —— 出于历史原因，这个阶段被称为 CRTC。

CRTC 控制所有和显示模式设置相关的内容。DRM 驱动会为 CRTC 硬件配置显示模式，同时将它和所有活动 plane、输出连接起来。我们也可以有多个 CRTC，每个都配置不同的设置。具体的配置只受硬件功能的限制。

plane 是堆叠的，因此它们可以互相重叠，或是覆盖输出的不同部分。根据配置的显示模式和每个 plane 的位置，CRTC 硬件会从各个 plane 读取像素数据，在必要时混合重叠的 plane，然后将结果转发给它的输出。

输出由 encoder 和 connector 表示。顾名思义，encoder 是将像素数据编码为输出格式的硬件组件。encoder 会和特定的 connector 关联，connector 代表到输出设备的物理连接，比如连接了显示器的 HDMI 或 VGA 接口。connector 还会提供输出设备支持的显示模式、物理分辨率、色彩空间这类信息。同一个 CRTC 的输出，会在不同的输出设备上镜像 CRTC 的屏幕内容。

#### 管道配置

决定如何连接和配置模式设置管道的各个阶段，这不是 DRM 驱动的工作，而是留给用户空间程序来完成，这就又回到了合成器。在初始化设置的过程中，合成器会打开 `/dev/dri` 下的设备文件，比如 `/dev/dri/card1`，然后调用对应的 ioctl \(\) 来配置显示管道。它还会从 connector 获取可用的显示模式，然后选择一个合适的。

当合成器完成第一个屏幕图像的渲染后，它会第一次配置模式设置管道。为此，它会为屏幕图像的缓冲对象创建一个 framebuffer，然后将这个 framebuffer 附加到一个 plane 上。接着，它会在 CRTC 上为自己的屏幕缓冲设置显示模式，连接管道的所有阶段 —— 从 framebuffer 到 connector，然后启用显示。

要在下一帧修改显示的图像，不需要完整的模式设置。合成器只需要将当前的 framebuffer 替换为新的即可，这被称为 page flipping。

模式设置管道的各个阶段可以用多种方式连接。一个 CRTC 可以镜像到多个 encoder，或是一个 framebuffer 可以被多个 CRTC scanout。这虽然提供了灵活性，但也意味着并非所有管道阶段的组合都是被支持的。

一个简单的实现会逐个应用每个阶段的设置：先在 CRTC 中配置显示模式，然后将所有缓冲对象上传到图形内存，接着为 scanout 设置 framebuffer 和 plane，最后启用 encoder 和 connector。如果这个过程中任何一步失败，屏幕就会保持关闭，或者（更糟的）处于失真的状态。比如，在设备内存有限的情况下，可能无法同时存储多个 plane 的 framebuffer，切换模式，甚至简单的 page flipping 都可能失败。显示更新失败，一直以来都是图形栈的常见问题。

DRM 的 atomic mode setting 在一定程度上解决了这个问题。模式设置代码会在一个名为 `drm\_atomic\_state` 的复合数据结构中，跟踪管道所有元素的完整状态，同时为管道的每个阶段维护子状态。这种模式设置是原子的：它要么应用所有管道阶段的完整复合状态，要么完全不应用。为了实现这一点，模式设置分为两个阶段：首先检查完整的新原子状态，然后，如果检查成功，就提交这个状态。

在检查阶段，DRM 核心、它的辅助工具以及 DRM 驱动，会根据可用图形硬件的限制和约束，测试提议的状态。比如，plane 需要验证附加的 framebuffer 是否是兼容的颜色格式，CRTC 需要验证给定的显示分辨率是否被硬件支持。如果检查成功，DRM 驱动会在提交阶段将新状态配置到硬件中。如果一个或多个阶段的状态检查失败，DRM 会停止模式设置操作，向用户空间程序返回错误。

因此，当我们的合成器想要配置显示模式时，它会设置所有管道阶段的原子状态，然后一次性全部应用。如果成功，显示输出就会相应地更新。对于连续的 page flipping 操作，合成器会复制当前的状态，将 framebuffer 替换为新的，然后应用新的状态。应用 page flipping 同样会在内核的 DRM 代码中触发原子检查 / 原子提交的流程，但开销比完整的模式设置操作要小得多。

DRM 的状态检查阶段独立于硬件的当前状态，不会修改它。如果原子状态检查失败，合成器会收到错误码，但显示输出不会有任何变化。合成器也可以在不提交的情况下验证原子状态，这让我们可以提前构建支持的配置列表。

#### 额外特性

在之前对 plane 的讨论中，我们假设硬件的所有 plane 都是相同的，但情况并非总是如此。通常会有一个 primary plane，用于 RGB 类的颜色格式，它会覆盖整个显示区域。合成器会设置 primary plane 来显示自己的屏幕图像。

但大多数硬件都会提供一个额外的 plane 用于鼠标指针，叫做 cursor plane。这个 plane 只覆盖很小的区域，会浮动在 primary plane 之上。顾名思义，合成器会用 cursor plane 来显示鼠标指针的图像，这样移动指针的时候，完全不需要修改 primary plane 的屏幕图像。

在 primary plane 和 cursor plane 之间，是 overlay plane，它们的尺寸各不相同，通常支持 YUV 类的颜色格式。这让它们非常适合以低 CPU 开销显示视频流。为此，视频播放器应用会向合成器提供包含 YUV 像素数据的缓冲对象。
