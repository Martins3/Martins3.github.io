# 为什么 drm 提供两个接口

调查 API 兼容性问到的，感觉这个回答很好，记录一下:

## 问题
对于 API 兼容性问题，为什么内核提供了两个 API :
- DRM_IOCTL_GET_CAP：查询内核、驱动能力；
- DRM_IOCTL_SET_CLIENT_CAP：声明当前客户端理解并希望使用的新行为。

我的问题是，难道提供 DRM_IOCTL_GET_CAP 就不能解决兼容性问题吗?
client 确认支持这个功能，那么就使用，如果不支持，那么不用这个 feature ，那么?
为什么还需要提供 DRM_IOCTL_SET_CLIENT_CAP

## 回答
核心原因是：内核支持新功能，不代表当前程序能正确处理新功能带来的对象、属性和语义变化。SET_CLIENT_CAP 让程序显式选择这些新行为，从而兼容旧程序。

以下以你当前的内核源码为准。

3. 为什么不能内核支持就自动开启？

最典型的例子是 UNIVERSAL_PLANES。

传统 KMS 接口中，不同类型的显示平面通过不同路径操作：

• 主画面通过 CRTC 相关接口配置。
• 光标通过 cursor 接口配置。
• plane 枚举接口主要返回 overlay。

因此，旧程序可能默认认为：“枚举到的 plane 都是 overlay，可以作为附加图层使用。”

后来内核统一了 plane 模型，把 primary、cursor 也表示成 plane。如果直接改变旧程序看到的枚举结果，旧程序就可能把主平面、光标平面当成 overlay，造成配置失
败或显示异常。

于是内核保留旧行为，只有程序声明：

drmSetClientCap(fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1);

才扩大它看到的 plane 范围。实际过滤就在 drm_mode_getplane_res() (drivers/gpu/drm/drm_plane.c:825)。

其他开关也有相同动机：

• 3D 模式：旧程序可能不理解立体布局，错误选择或使用这些模式。
• Writeback connector：它的用途是输出到内存，旧程序可能把它当成普通显示器接口。
• 颜色流水线：新旧颜色属性存在语义冲突，需要明确选择使用哪套规则。

4. 它改变的是当前客户端的接口行为

SET_CLIENT_CAP 的状态保存在当前打开实例对应的 struct drm_file 中，例如：

```txt
file_priv->universal_planes = req->value;
file_priv->atomic = req->value;
```

所以：

• 不会全局切换显卡，也不会替其他独立打开设备的客户端开启功能。
• 共享同一个打开实例的 fd，例如 dup() 得到的 fd，会共享这些状态。
• 开启 atomic 不会立即修改显示配置；后续还需要提交具体配置。
• 驱动不支持相应功能时，设置会失败。

另外，这两个 ioctl 的能力列表不是一一对应的。例如没有通用的 DRM_CAP_ATOMIC 查询项，程序通常直接尝试：

```txt
int ret = drmSetClientCap(fd, DRM_CLIENT_CAP_ATOMIC, 1);
if (ret == 0) {
    /* 可以继续枚举 atomic 属性并使用 atomic 接口 */
} else {
    /* 根据错误处理，必要时退回 legacy KMS */
}
```

这里一次调用同时完成了“检查是否可用”和“声明客户端接受新行为”。

## 总结

2026-09-29 其实这个问题很容易理解，就像是 neovim 一样，feature 不是默认打开的，仅此而已。
