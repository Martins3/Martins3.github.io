## cuda async barrier
<!-- bc7434a4-37ba-43f4-8cb8-b4b49304d5a5 -->

`Asynchronous Barriers` 可以先理解成：

> 它是“可拆开的 `__syncthreads()`”。

传统 `__syncthreads()` 是：

- 线程走到这里
- 全部停下
- 等所有线程都到齐
- 再一起往后走

而异步屏障是：

- 线程先声明“我到了” -> `arrive()`
- 但先不一定停下
- 可以继续做一点与共享数据无关的工作
- 真到需要用共享结果时，再 `wait()`

所以它的核心价值不是“同步更快”，而是：

- **把同步拆成两段**
- **让同步等待和独立计算重叠**

## 为什么会需要它

如果你只是做一个最普通的 block 内同步，那么 `__syncthreads()` 通常已经够用了，而且往往更直接。

异步屏障真正有价值的场景是：

1. 某些线程先到同步点，但后面还有一些独立计算可以做。
2. 线程块里不同 warp 分工不同，比如有的负责搬数据，有的负责算数据。

## 先建立一个最重要的心智模型

把 barrier 想成一个带计数器的“关卡”。

初始化时你告诉它：

- 这一轮需要多少次到达

例如：

```cpp
init(&bar, block.size());
```

意思就是：

- 这一轮需要整个 block 的线程都到达

之后每次 `arrive()`：

- 屏障内部计数减 1
- 调用线程先拿到一个 token
- 线程本身**不阻塞**

当计数减到 0：

- 这一轮 barrier 完成
- barrier 自动切到下一轮，也就是下一 phase

而 `wait(token)` 的意思是：

- 我现在要确认“我刚才参与的那一轮”已经真的结束了

所以你可以把 `token` 理解成：

- “我是在第几轮到达的”这个凭证

---

## 和 `__syncthreads()` 的区别

最简单的对比是：

| 机制              | 到达时会不会立刻停下 | 能不能在同步间隙继续做事 | 适合什么场景                  |
|-------------------|----------------------|--------------------------|-------------------------------|
| `__syncthreads()` | 会                   | 不能                     | 普通 block 内同步             |
| `cuda::barrier`   | 不一定               | 能                       | 需要 split arrive/wait 的场景 |

所以你可以把它们的差别概括成：

- `__syncthreads()` 是“到点立刻排队”
- `cuda::barrier` 是“先签到，再决定什么时候真正等”

## 这个目录里的示例到底在演示什么

`chapter_demo.cu` 里真正想演示的重点非常简单：

1. 每个线程先算自己的 `local`
2. 调用 `bar.arrive()`
3. 在 `arrive()` 和 `wait()` 之间，再做一点独立计算
4. 最后 `bar.wait(token)`，等整个 block 都到齐

也就是这段逻辑：

```cpp
auto token = bar.arrive();
float processed = local * 0.5f;
bar.wait(std::move(token));
```

这里最值得抓住的不是结果数值，而是顺序：

- `local` 是当前线程自己的局部结果
- `processed = local * 0.5f` 不依赖别的线程，所以可以插在中间
- 真正依赖“大家都已经到齐”的地方，是 `wait()` 之后

这就是 async barrier 的精髓：

- **先报到**
- **中间塞一点独立工作**
- **需要汇合时再等**

如果换成 `__syncthreads()`，那就是线程一到同步点就停住，没法把这段独立工作塞进去。

## 这个 API 该怎么读

### 1. 初始化

```cpp
__shared__ cuda::barrier<cuda::thread_scope_block> bar;
auto block = cooperative_groups::this_thread_block();

if (block.thread_rank() == 0) {
    init(&bar, block.size());
}
block.sync();
```

这里要注意两件事：

- barrier 通常放在 `__shared__` 里，因为它是 block 内共享对象
- 一个线程初始化之后，必须再做一次同步，确保别的线程看到的是“已经初始化好的 barrier”

这一步常被叫做 bootstrap。

### 2. `arrive()`

```cpp
auto token = bar.arrive();
```

含义：

- 我已经完成了本轮到达
- 请把 barrier 的计数减下去
- 顺便给我一个 token，后面 `wait()` 要用

重点是：

- `arrive()` **默认不阻塞**

### 3. `wait(token)`

```cpp
bar.wait(std::move(token));
```

含义：

- 等待 token 对应的那一轮 barrier 完成

如果那一轮已经结束了：

- 它会立刻返回

如果还没结束：

- 它才会阻塞

### 4. `arrive_and_drop()`

这是给“后续不再参与同步的线程”准备的。

如果某个线程之后不玩了，不能直接 `return`，否则别的线程还会一直等它。

正确做法是：

```cpp
bar.arrive_and_drop();
return;
```

它的意思是：

- 当前这一轮我算到达了
- 从下一轮开始不要再把我算进 expected count

## phase 和 token 到底该怎么理解

很多人第一次看 barrier 会卡在 `phase` 和 `token` 这两个词上，其实可以简单理解。

### phase

phase 就是“第几轮同步”。

比如循环里反复使用同一个 barrier：

- 第一轮所有线程到齐 -> 第一轮 phase 完成
- barrier 自动重置
- 第二轮继续计数

所以 barrier 不是一次性用品，它是“按轮次循环使用”的。

### token

token 就是在说：

- “我是在这一轮 arrive 的”

所以 `wait(token)` 不是泛泛地“等这个 barrier”，而是：

- **等我刚才参与的那一轮 barrier 完成**

这也是为什么 token 不能乱跨很多轮保存后再用。

## 最容易踩坑的地方

### 1. 初始化后忘记再同步

错误写法本质是：

- 线程 0 还没初始化完
- 其他线程已经开始 `arrive()`

这样 barrier 状态就不可信了，轻则结果不对，重则死锁。

### 2. 以为它适合所有同步

不是。

如果你只是“整个 block 在这里等一下”，那还是优先想 `__syncthreads()`。

异步屏障的收益来自：

- `arrive()` 和 `wait()` 之间那段可重叠的工作

如果这段工作根本不存在，那你只是把代码写复杂了。

### 3. 线程提前退出但没 `arrive_and_drop()`

这会让别的线程永远等一个已经退出的线程。

### 4. 在不支持的架构上直接用

`cuda::barrier` 需要 `sm_70+`。

这个目录的示例专门处理了兼容性问题：

- 设备端只有 `sm_70+` 才真的编译 barrier 逻辑
- `sm_61` 上走的是 `traditional_sync_kernel`

所以这个 demo 的重点不是“在 GTX 1060 上跑出真正的 async barrier”，而是：

- **让代码结构先讲清楚**
- **让旧卡也能编译和运行一个可对照的版本**

### 5. warp 发散后直接 `arrive()`

这是官方文档里一个很容易被忽略、但很关键的点。

如果一个 warp 在 `arrive()` 前发生了分支发散，那么 barrier 的到达计数行为会变复杂，不一定还是你直觉上的“整个 warp 算一次”。

所以经验上要记住：

- 如果 `arrive()` 前有明显的 warp 分支发散，要非常小心
- 必要时先 `__syncwarp()`
