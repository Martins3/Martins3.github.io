## 从 cuda::barrier 到 mbarrier
<!-- 066d72fe-a839-4d23-a2df-11853d76ba43 -->

`2.md` 从使用者的角度讲了 `cuda::barrier` 的语义、API 和典型模式。
这篇文档往下再走一层，看看 **mbarrier** —— 也就是 `cuda::barrier` 在 GPU 硬件和 PTX 指令层面的实现原语。

理解 mbarrier 不是为了让你把所有代码都改写成内联汇编，而是为了让你在面对复杂同步场景、性能瓶颈或 `cuda::barrier` 无法直接表达的需求时，知道底层在发生什么。

## mbarrier 是什么

简单一句话：

> **`cuda::barrier` 是 C++ 标准风格的包装，`mbarrier` 是 GPU 硬件真正执行的指令。**

当你在设备端写下：

```cpp
auto token = bar.arrive();
bar.wait(std::move(token));
```

编译器最终生成的 PTX（或 SASS）大致对应：

```ptx
mbarrier.arrive.shared.b64          %token, [%bar];
// ... 中间可能插入独立计算 ...
mbarrier.wait.acquire.shared.b64    [%bar], %token;
```

mbarrier 指令从 **sm_70（Volta）** 开始引入，是 NVIDIA 为异步屏障提供的原生硬件支持。没有这条指令，异步屏障只能靠软件自旋 + 原子操作模拟，性能和功能都差很多。

---

## 为什么要了解 mbarrier

如果你只用 `cuda::barrier`，理论上不需要关心 PTX。但以下三种情况，了解 mbarrier 会很有帮助：

| 场景 | 原因 |
|------|------|
| **调试同步死锁** | `cuda::barrier` 的报错信息往往只到 API 层；理解 mbarrier 的 phase/token 机制才能判断是计数错误还是 parity 错位 |
| **性能极致优化** | PTX 层可以精确控制 memory ordering（`.release` / `.acquire`），而 `cuda::barrier` 帮你做了默认选择 |
| **使用 TMA / 异步拷贝** | `arrive_expect_tx` 这类事务跟踪指令在 `cuda::barrier` 中没有直接等价的高层封装，必须接触 PTX |

---

## mbarrier 的硬件视图

mbarrier 对象本质上是一块 **64-bit 的 shared memory**，内部由硬件解释为一个结构化状态：

```
+----------------+----------------+
|   高 32 bit    |   低 32 bit    |
+----------------+----------------+
|  计数/状态位   |  事务计数/预留  |
+----------------+----------------+
```

注意：具体的位域分配 NVIDIA 并未完全公开，但开发者需要知道的是：

1. mbarrier 必须放在 **shared memory** 里（`.space = .shared`）。
2. 它占用 **8 字节**，需要 8 字节对齐。
3. 硬件直接维护内部的 phase 和 countdown，而不是靠软件轮询。

这意味着 mbarrier 的 `wait` 在硬件层面可以是真正的 **阻塞等待**（让出 warp 执行资源），而不是消耗指令的自旋锁。这是它和软件 barrier 最根本的性能差异。

---

## 核心 PTX 指令

PTX 层面的 mbarrier 指令族主要包括以下几条：

### 1. `mbarrier.init`

```ptx
mbarrier.init.shared.b64 [%bar], %expected_count;
```

对应 `cuda::barrier` 的：

```cpp
init(&bar, expected_count);
```

语义完全一致：把 barrier 的 expected arrival count 设为指定值，phase 重置为 0（偶 phase）。

**注意**：和 C++ API 一样，初始化后仍然需要一次 bootstrap sync（`__syncthreads()`），确保所有线程看到初始化后的内存状态。

### 2. `mbarrier.arrive`

```ptx
mbarrier.arrive.shared.b64 %token, [%bar];
```

对应：

```cpp
auto token = bar.arrive();
```

PTX 层面的 `token` 不是一个 C++ 对象，而是一个寄存器值（通常是 32-bit 整数），内部编码了 **当前 phase** 的信息。

关键行为：
- 原子递减 barrier 的内部计数器。
- 返回当前 phase 标识，供后续 `wait` 使用。
- **不阻塞**。

### 3. `mbarrier.arrive.expect_tx`（sm_90+）

```ptx
mbarrier.arrive.expect_tx.shared.b64 %token, [%bar], %tx_count;
```

这是 mbarrier 超越 `cuda::barrier` 标准 API 的一个重要扩展。

它表示：
- 本线程到达 barrier。
- 同时声明还有 **%tx_count 字节的异步内存事务** 尚未完成。

barrier 不仅要等所有线程到达，还要等这些事务全部完成后，phase 才算结束。典型配合对象是 **TMA（Tensor Memory Accelerator）** 或 `cp.async` 指令族。

`cuda::barrier` 在较新版本中通过 `cuda::device::barrier_arrive_tx` 提供了封装，但底层走的仍是这条 PTX 指令。

### 4. `mbarrier.wait`

```ptx
mbarrier.wait.acquire.shared.b64 [%bar], %token;
```

对应：

```cpp
bar.wait(std::move(token));
```

语义：
- 比较 `%token` 中的 phase 和 barrier 当前 phase。
- 如果 barrier 已完成该 phase（进入了下一 phase），**立即返回**。
- 否则，**阻塞当前线程**，直到 phase 推进。

`.acquire` 后缀表示这条指令带有 **acquire 语义**：wait 返回后，调用线程可以保证看到之前所有到达线程在 `arrive()` 之前的内存写入。

### 5. `mbarrier.try_wait.parity`

```ptx
mbarrier.try_wait.parity.acquire.shared.b64 %pred, [%bar], %parity;
```

对应 `cuda::ptx::mbarrier_try_wait_parity`。这是**无 token 等待**版本：

- `%parity` 是一个 0 或 1 的值。
- 线程检查 barrier 的当前 phase 奇偶性是否已经变成 `%parity`。
- 如果已经翻转，`%pred = 1`，指令成功。
- 如果还没翻转，`%pred = 0`，线程**不阻塞**，调用者需要自己重试（通常配合循环实现自旋）。

为什么需要 parity 而不是直接用 phase 编号？因为 phase 编号可能很大，而硬件只需要一个 bit 来区分"本轮"和"下一轮"。parity 机制让单线程可以用极简的状态（一个 bool）轮询 barrier，不需要保存完整的 token。

## `cuda::barrier` 到 PTX mbarrier 的映射

| `cuda::barrier` API | PTX 指令 | 说明 |
|---------------------|----------|------|
| `init(&bar, n)` | `mbarrier.init.shared.b64` | 初始化 expected count |
| `bar.arrive()` | `mbarrier.arrive.shared.b64` | 非阻塞到达，返回 token |
| `bar.wait(token)` | `mbarrier.wait.acquire.shared.b64` | 阻塞等待对应 phase 完成 |
| `bar.arrive_and_drop()` | `mbarrier.arrive.shared.b64` + 软件维护 expected count | C++ 层封装了 count 减一和到达 |
| `barrier_arrive_tx(...)` | `mbarrier.arrive.expect_tx.shared.b64` | sm_90+ 事务跟踪 |
| parity 轮询 | `mbarrier.try_wait.parity.acquire.shared.b64` | 无 token 忙等 |

## 用 PTX mbarrier 重写核心逻辑

下面是 `chapter_demo.cu` 中 split arrive/wait 模式的 PTX 等价写法（概念层面，使用 `cuda::ptx` 封装而非纯内联汇编）：

```cpp
#if __CUDA_ARCH__ >= 700
#include <cuda/ptx>

__global__ void mbarrier_ptx_kernel(float *out, int n) {
    // mbarrier 是 64-bit shared memory 对象
    __shared__ alignas(8) uint64_t bar;
    auto block = cooperative_groups::this_thread_block();

    // 1. 初始化（单线程）
    if (block.thread_rank() == 0) {
        cuda::ptx::mbarrier_init(&bar, block.size());
    }
    block.sync();  // bootstrap

    // 2. 局部计算
    float local = 0.0f;
    for (int i = block.thread_rank(); i < n; i += block.size()) {
        local += static_cast<float>(i);
    }

    // 3. arrive：返回 token（PTX 层是 uint32_t 编码）
    auto token = cuda::ptx::mbarrier_arrive(&bar);

    // 4. arrive/wait 间隙的独立计算
    float processed = local * 0.5f;

    // 5. wait：阻塞直到 phase 完成
    cuda::ptx::mbarrier_wait(&bar, token);

    // 6. 同步后使用共享数据
    __shared__ float shared_val;
    if (block.thread_rank() == 0) {
        shared_val = processed;
    }
    block.sync();
    out[block.thread_rank()] = shared_val + local;
}
#endif
```

这段代码和 `cuda::barrier` 版本的语义**几乎完全一致**，但有几个细微差别值得注意：

1. **barrier 是裸的 `uint64_t`**，没有 C++ 类的封装，初始化和对齐需要手动处理。
2. **token 是底层编码值**，不是一个 RAII 对象，没有 `std::move` 语义，但同样不能跨 phase 复用。
3. **`mbarrier_wait` 隐含 acquire 语义**，等价于 `bar.wait()` 的默认内存序。

## Phase Parity 的硬件真相

`2.md` 里提到 phase 是"第几轮同步"，token 是"参与凭证"。在硬件层面，phase 不是一个大整数，而是一个在 barrier 64-bit 状态内部维护的计数器，**每次 barrier 完成后自动递增**。

但硬件暴露给 `wait` 的不是完整 phase 值，而是 **phase parity（奇偶性）**。原因很实际：

- 如果一个线程保存了一个旧 token，然后在很多轮之后才调用 `wait`，它持有的 phase 编号可能已经溢出或失效。
- parity 只有 1 bit，天然具有"模 2 回绕"的特性：无论经过多少轮，"奇"和"偶"永远交替。
- `mbarrier.try_wait.parity` 让单线程可以用一个 `bool parity = 0` 循环轮询，代码极简。

所以 parity 版本的本质是：

> 我不关心具体是第几轮，我只关心"我参与的那一轮是否已经结束了"。而一轮结束的标志，就是 parity 从 0 变 1 或从 1 变 0。

## Memory Ordering：Release 与 Acquire

PTX mbarrier 指令显式携带 memory ordering 修饰符，这是 `cuda::barrier` 帮你隐藏的细节：

| PTX 后缀 | 含义 | 对应 C++ 内存序 |
|----------|------|----------------|
| `.release` | arrive 前的写入对后续 wait 线程可见 | `std::memory_order_release` |
| `.acquire` | wait 返回后能看到之前 release 的写入 | `std::memory_order_acquire` |
| `.relaxed` | 无额外内存序保证 | `std::memory_order_relaxed` |

`mbarrier.arrive` 默认带有 `.release` 语义（或等价效果），确保到达线程在 `arrive()` 之前对 shared/global memory 的写入，对后来 `wait()` 成功的线程可见。

`mbarrier.wait` 默认使用 `.acquire`，确保 `wait()` 返回后，调用线程能正确读到之前到达线程写入的数据。

这个 release-acquire 对恰好构成了一个 **happens-before 关系**，是异步屏障保证内存一致性的核心。

## 什么时候用 PTX，什么时候用 `cuda::barrier`

| 情况 | 推荐选择 | 理由 |
|------|----------|------|
| 普通 block 内 split arrive/wait | `cuda::barrier` | 类型安全，不易出错 |
| 需要事务跟踪（TMA / cp.async） | `cuda::ptx::mbarrier_*` 或专用 API | `cuda::barrier` 标准接口不暴露 tx count |
| 极致性能调优，需要控制 memory order | `cuda::ptx::mbarrier_*` | 可选 `.relaxed` 减少 fence 开销 |
| 无 token 轮询（parity wait） | `cuda::ptx::mbarrier_try_wait_parity` | `cuda::barrier` 不提供 parity 接口 |
| Warp specialization / 复杂生产者-消费者 | 两者皆可 | `cuda::barrier` 通常够用；需要 tx tracking 时切 PTX |

## PTX 层面特有的踩坑点

### 1. 手动对齐

`cuda::barrier` 类内部处理了对齐；裸 `uint64_t` barrier 需要显式：

```cpp
__shared__ alignas(8) uint64_t bar;
```

否则未对齐访问可能导致未定义行为或性能损失。

### 2. Token 类型混淆

`cuda::barrier` 的 token 是 `arrival_token` 类；PTX 层是原始整数。不要混用：

```cpp
// 错误：不能把 cuda::barrier 的 token 传给 PTX wait
auto token = bar.arrive();  // cuda::barrier 版本
cuda::ptx::mbarrier_wait(&raw_bar, token);  // 类型不匹配！
```

### 3. Parity 轮询不是阻塞等待

`mbarrier.try_wait.parity` 在条件不满足时**立即返回失败**，不会挂起线程。如果写成：

```cpp
cuda::ptx::mbarrier_try_wait_parity(&bar, parity);  // 失败也不阻塞
```

而没有检查返回值，代码会继续往下执行，导致数据竞争。正确做法是：

```cpp
while (!cuda::ptx::mbarrier_try_wait_parity(&bar, parity)) {
    // 可选：插入 __nanosleep 避免忙等占满 issue slot
}
```

### 4. `.relaxed` 的陷阱

如果你为了性能使用 `.relaxed` 版本的 arrive/wait，必须自己额外插入 `fence` 指令保证内存可见性。除非你对 GPU memory model 非常熟悉，否则不要这样做。

---

## 一句话总结

> **`cuda::barrier` 是 mbarrier 的 C++ 面孔，mbarrier 是 `cuda::barrier` 的硬件灵魂。** 日常写代码用 C++ API；遇到 TMA 事务跟踪、parity 轮询、或需要细粒度 memory ordering 控制时，再下到 PTX 层。

理解 mbarrier 的指令语义，不是为了写更复杂的代码，而是为了在异步同步出问题时，知道该往哪看。
